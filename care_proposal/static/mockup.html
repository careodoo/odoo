# Care Proposal — Redesign & Full-Screen Mockup (v1 Draft)

> Goal: a fast, easy, accurate, deep pricing & proposal system with a strong
> dashboard, strong CRM link, per-customer service costs, frozen historical
> pricing, duplication/revisions, and per-company service-type-aware reports.

---

## 0. Root problems found in the current module (why we redesign)

| # | Problem | Evidence |
|---|---------|----------|
| 1 | **Old proposals change when a service cost is edited** | `proposal.service.line.total_cost` is a `related` live-link (proposal_service_line.py:18-20); `compute_service_amounts()` reads the **live master** `line_ids` (proposal.py:270-298) |
| 2 | **Same service can't cost differently per customer** | `proposal.service` is global, has no `partner_id` (proposal_service.py) |
| 3 | **No duplicate / revision feature** | no `copy()` / action |
| 4 | **No dashboard / analytics** | no OWL dashboard in static/ |
| 5 | **Weak CRM link** | only `lead_id` + count; no stage/revenue/win-loss sync (crm_lead.py) |
| 6 | **Report price table mismatched to service type** | hard-coded manpower columns for all rows (customer_proposal.xml:164-210) |
| 7 | **Reports not per-company** | hard-coded logos (customer_proposal.xml:39-42) |
| 8 | Tangled totals, duplicate material/equipment models, hard-coded 10 cost types in 3 files, no currency, no search view, unreachable `contracted` state, manual `total_commission_amount`, barcode collision bug | multiple |

## 1. New architecture (the backbone of the mockup)

```
                         ┌─────────────────────────────┐
                         │  SERVICE CATALOG (master)   │   definition only:
                         │  proposal.service           │   name, type, UoM,
                         │  + cost COMPONENT template   │   default structure
                         └──────────────┬──────────────┘
                                        │ has many dated cost versions /
                                        │ per-customer overrides
                         ┌──────────────▼──────────────┐
                         │  COST BOOK (per customer)   │   proposal.service.cost
                         │  partner_id (or "default"), │   effective_date, currency
                         │  component rows + amounts    │   → "this service costs X
                         └──────────────┬──────────────┘     for THIS customer"
                                        │  pick + FREEZE (snapshot)
                                        ▼
   ┌───────────────────────────────────────────────────────────────────────┐
   │  PROPOSAL  (proposal.proposal)                                          │
   │   service lines → SNAPSHOT of component costs (frozen, never re-reads)  │
   │   cost lines (unified material/equipment/...) → snapshot                │
   │   pricing = cost  +  margin strategy  →  customer price                 │
   │   revision_of_id / version, duplicate(), currency_id (Monetary)        │
   └───────────────────────────────────────────────────────────────────────┘
```

**Three rules that kill the #1 bug:**
1. The proposal stores its **own copy** of every cost component (snapshot at add-time).
2. Totals compute **only** from proposal-local snapshots — never from the master.
3. A "Re-sync from catalog" button is the *only* way master changes enter an existing proposal (explicit, never silent).

**Per-customer cost:** the Cost Book keyed by `(service, partner, effective_date)`; a "default" book is the fallback. Picking a service in a proposal pulls the right book for that customer & date, then freezes it.
